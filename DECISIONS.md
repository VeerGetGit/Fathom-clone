# Decisions

Engineering and product decisions for Fathom8x, and the trade-offs behind them.

## Why Fathom over Amazon and Higgsfield

I chose Fathom for five reasons:

1. **Prior experience match.** My HCP CRM project used React + FastAPI + LangGraph + Groq + Supabase, which maps directly to Fathom's stack. My Agentic RAG Chatbot involved summarization and text extraction from documents. I had built the core building blocks before and knew I could execute well.

2. **I used the real product first.** I signed up, connected Zoom, recorded two real meetings, and tested every flow: transcript, summary templates, Ask Fathom, search, share, action items. I understood what I was building before writing a line of code.

3. **Higgsfield was not cloneable in 24 hours.** Its core value is proprietary AI video generation models (Seedance 2.5, Genjutsu). Without those models, a clone is an empty UI. There is no way to fake the actual product.

4. **Amazon's scope is too large.** Search, product pages, cart, checkout, recommendations, filters, reviews. Covering all flows properly in 24 hours is not feasible. The result would be incomplete and feel shallow.

5. **Fathom's intelligence layer is achievable.** Transcript to summary to chat is text-to-text, which Groq handles well. The recording bot can be legitimately stubbed per the brief. The scope is right for 24 hours and I could build it to a high standard.

## Why stubbing the recording layer was the right call

A real recording pipeline means a meeting bot joining Zoom, Meet and Teams, calendar OAuth, media storage,
transcription and speaker diarization. Each is its own project, with its own failure modes and costs, and
none of them is what a user judges the product on. Everything a user sees starts after a transcript exists.

So I seeded four realistic meetings (a roadmap review, a sales demo, a 1:1 and an architecture
discussion) with full transcripts, and built every downstream feature for real: the summary and highlights are
generated by the model, search runs against the database, and chat calls the LLM live. The stub sits at one
clean seam, the `transcript_segments` table. A real ingestion pipeline would write to the same tables and
nothing above it would change.

The four meetings differ in length (20 to 60 minutes), participant count (2 to 5) and type, which is
enough to exercise the Sales template, screen-share events and per-speaker rendering.

## Why Groq and `openai/gpt-oss-120b`

- **Speed.** Groq's inference is fast, and chat and summary generation are interactive. A multi-second
  wait on every question would make the product feel broken.
- **Context size.** A transcript of an hour-long call fits in the context window, so Ask Fathom8x can pass the
  entire transcript. That avoids building chunking, embeddings and a vector store, and it avoids the
  retrieval misses those bring.
- **Quality for the task.** Summarizing and answering questions from a given text doesn't need a frontier
  model. A 120B open-weight model handled it well in my testing (for example, correctly answering who owns
  the data backfill and by when).
- **Cost and access.** Open-weight model, accessible through a simple API with a free tier.

Settings: `reasoning_effort="low"` to keep latency down, `json_object` response format for summaries, and
low temperature (0.3) so answers stay close to the transcript. Summary output is parsed defensively, because a
model can still return JSON wrapped in prose.

## Data model

Seven tables in Postgres (Supabase). The full SQL is in `database/schema.sql`.

- **`meetings`**: includes a unique `share_token`, so sharing needs no extra table.
- **`participants`**: per meeting, with a colour used for speaker bubbles and avatars.
- **`transcript_segments`**: one row per line of speech *or* per screen-share event, distinguished by
  `segment_type`. Storing screen sharing in the same table keeps ordering trivial: the transcript, the
  inline badges and the sidebar all read one ordered list.
- **`summaries`**: unique on (meeting, template). Each template is generated once and cached, so switching
  templates is instant after the first view. `key_takeaways` is JSONB because it is a short ordered list that is
  always read whole.
- **`highlights`**: belong to a summary, so each template has its own set of clickable timestamps.
- **`action_items`**: assignee and timestamp are optional, which is what lets users add their own.
- **`chat_messages`**: `meeting_id` is null for the global chat, so one table serves both chats.

Other decisions:
- **Full-text search** uses generated `tsvector` columns with GIN indexes and a `search_meetings` SQL function.
  The API adds a substring fallback, because full-text search only matches whole words and users type partial
  ones.
- **Cascade deletes** from `meetings`, so reseeding is one delete.
- **No users table**, as a consequence of skipping auth.
- Durations and timestamps are stored in seconds, and formatting happens in the UI.

## What I would build next

Roughly in priority order:

1. **Authentication and per-user data**, then Row Level Security with a service-role key on the server. This
   is the biggest gap and unlocks Team Calls, Playlists and Alerts.
2. **Prompt-injection hardening.** The model is told to answer only from the transcript, but transcript text
   and user messages are not isolated from instructions. I would delimit untrusted content, add output checks,
   and test with adversarial transcripts.
3. **Real recording ingestion**: a meeting-bot provider and a transcription service writing to
   `transcript_segments`, with real per-call video.
4. **Retrieval for the global chat.** It currently sends every transcript on every question. Embeddings and
   retrieval would make it scale beyond a handful of meetings and allow source citations.
5. **Streaming responses** for chat and summaries, so text appears as it is generated.
6. **Tests**: API tests against a test database, and component tests for the transcript and summary tabs.
7. **Smaller things**: editing and assigning action items, pagination, Customize presets, and transcript
   export to a file.

## Trade-offs

| Decision | Gain | Cost |
|---|---|---|
| Seeded data instead of a recording bot | A complete, demonstrable product in the time available | Nothing is captured from real calls |
| Whole transcript in the prompt (no RAG) | Simple, accurate, no retrieval misses | Doesn't scale to many meetings or very long calls |
| Row Level Security off, anon key on the server | Simple setup with no auth | Anyone with the anon key can read and write the tables; fine for a demo, not for customer data |
| Summaries generated lazily and cached | Fast after first view; no wasted generation | The first view of a new template waits on the model |
| One sample video for every meeting | Works without hosting media | Seeking is proportional, not exact; depends on a third-party host |
| Dates seeded relative to "now" | Dashboard groups look right on any day | Dates are fixed after seeding, so they drift until `--dates` is re-run |
| Free-tier hosting | No cost | Cold starts of up to a minute on the backend |
| Plain request/response chat, no streaming | Simpler code | Answers appear all at once |
| Limited prompt protection | Faster to build | Chat is not hardened against malicious transcript content |
